# Заметки по безопасности (бэклог)

**Статус:** заметка на будущее. Это не принятое решение и не инструкция к немедленным
изменениям, а зафиксированный результат обсуждения от 2026-11-06, чтобы не потерять
контекст и приоритеты.

## Контекст

Обсуждался перенос формы входа админа на `/admin` и отдельный админский API. Вывод:
сам по себе скрытый URL `/admin` ничего не даёт — это security through obscurity.
Польза появляется только от отдельных токенов, отдельных политик и реальных проверок
на сервере.

## Что уже есть в проекте

- JWT access/refresh в httpOnly-куках; `mp_role` и `mp_user_id` — не httpOnly,
  только для UI.
- API-роуты используют `withAuth`, `withOptionalAuth`, `withRole`, `withAdmin`.
- Валидация входных данных через zod (`src/lib/validate.ts`).
- Админ определяется по `ADMIN_EMAIL` и `ADMIN_PASSWORD_HASH`, пароль сверяется через bcrypt.
- Логин отвечает нейтрально («Invalid credentials»), не раскрывая существование аккаунта.
- Страницы `/admin/*` проверяют роль на клиенте; данные защищены на уровне API.

## Чего пока нет

- Ограничения частоты попыток входа и запросов к API (rate limiting).
- Отдельных токенов/политик для админа.
- 2FA для админского аккаунта.
- Аудита админских действий.
- Серверного guard для страниц `/admin/*` (middleware или SSR-редирект).
- Аудита владения ресурсами по всем пользовательским ручкам.

## Приоритеты

### 1. Дешёвое и важное

- [ ] Rate limiting на `/api/auth/login` (и на админский вход, когда он появится).
- [ ] Аудит пользовательских API на владение ресурсом: participant должен читать и менять
      только свои отчёты, записи, сообщения и т.п., а не данные по чужому `id`.
- [ ] Серверный guard для `/admin/*` — для UX и defense in depth; данные всё равно
      защищать в API.
- [ ] `noindex, nofollow` для админских страниц.
- [ ] Не отдавать клиенту лишние поля (хеши, чужие email, внутренние идентификаторы).
- [ ] Проверить массовое присваивание: клиент не должен передавать `role`, `mentorId`,
      `status` и другие служебные поля.

### 2. Отделение админки

- [ ] Отдельные токены/куки для админа с собственной аудиторией (`aud: 'admin'`).
      Админский токен не должен приниматься пользовательскими API, и наоборот.
- [ ] Отдельный вход `/api/admin/auth/login` со своим rate limit и логом.
- [ ] 2FA (TOTP) для админского аккаунта.
- [ ] Аудит админских действий: кто, что, когда, с какого IP.
- [ ] Более короткая сессия для админа.

### 3. Инфраструктурное

- [ ] Вынос админки на отдельный поддомен — реальная изоляция кук и снижение последствий XSS.
- [ ] Rate limiting по типам ручек: отдельно логин, отдельно создание отчётов,
      отдельно поиск продуктов.

## Принципы для пользовательских API

Каждая ручка должна делать только то, для чего она существует:

- роль проверена;
- ресурс принадлежит текущему пользователю;
- HTTP-метод соответствует операции;
- входные данные провалидированы;
- ответ не содержит лишних данных;
- частота вызовов ограничена;
- ошибки не раскрывают существование чужих сущностей.
