План собран по утверждённым пунктам. Каждый пункт — что делаем и как это поймёт исполнитель.
Статусы: **подтверждено** / **изменено** / **новое**.

## 1. Несколько файлов к дню: аудио **и** видео

**Статус: изменено (расширено).**

Сейчас к дню можно прикрепить одно аудио и одно видео. Надо: **несколько аудио** и **несколько
видео** на каждый день марафона. Ментор загружает, участник видит список плееров, админ видит все файлы.

**Что есть сейчас.**
- `TemplateDay.audioUrl` — одно аудио (`POST /api/uploads/audio`).
- `TemplateDay.videoId` — одно видео Kinescope (вставка ссылки).
- Участник: `DayMaterials.tsx` — один аудио-плеер и один `KinescopePlayer`.
- Ментор: `src/pages/mentor/templates/[id]/days.tsx` — одно аудио, одна видео-ссылка.

**Что делаем.**
- БД: таблица вложений `template_attachments` (общая для дней и предстартовой страницы, п.7):

  | Поле | Тип | Описание |
  |---|---|---|
  | id | UUID PK | |
  | templateId | UUID FK → `marathon_templates(id)` CASCADE | Шаблон |
  | templateDayId | UUID FK → `template_days(id)` CASCADE, NULL | День (NULL = предстартовые) |
  | scope | enum `intro`/`day` | Где показывается |
  | kind | enum `audio`/`video`/`file` | Тип вложения |
  | url | string | Аудио/файл — путь `/api/uploads/…`; видео — `videoId` Kinescope |
  | fileName | string | Исходное имя файла |
  | mimeType | string | MIME |
  | sizeBytes | integer | Размер |
  | position | integer | Порядок вывода |
  | createdAt | datetime | |

  - Миграция: перенести `audioUrl`/`videoId` из `template_days` во вложения.
  - **Ограничение:** текущее поведение `POST /days` (удалить все дни шаблона и создать заново)
    **сохраняется**. Если редактировать шаблон, у которого уже есть прикреплённые к дням
    материалы, связи с этими материалами потеряются. На этом этапе осознанно не решаем —
    при необходимости существенно изменить наполнение проще создать новый шаблон/марафон.
- Uploads API: `POST /api/uploads/audio` — несколько файлов; видео — несколько ссылок Kinescope;
  `POST /api/uploads/file` — документы (п.2). Для предстартовых — тот же API со `scope=intro`.
  Upload возвращает метаданные файла (`url`, `fileName`, `mimeType`, `sizeBytes`); строки
  `template_attachments` создаются/синхронизируются при сохранении дней (`POST /days`) или
  шаблона (`PUT /api/marathons/[id]`).
- API шаблона: `GET/POST /api/marathons/[id]/days` — `attachments[]`; `GET/PUT /api/marathons/[id]`
  — `introAttachments[]`.
- Frontend: ментор — блоки «Аудио»/«Видео» с добавлением и удалением файлов; участник — списки
  плееров; админ — показ всех вложений.

## 2. Материалы дня: Quill-текст **и** PDF

**Статус: изменено (уточнено после обсуждения).**

Текст дня всегда редактируется в **визуальном редакторе (Quill)**. Варианта «простой текст»
и настройки шаблона `text_editor: plain | quill` **нет**.

К дню можно прикрепить **и текст, и PDF одновременно**:
- текст демонстрируется в своём блоке (санированный HTML от Quill);
- PDF-файлы располагаются под текстом отдельным списком «Документы (PDF)»;
- PDF открывается обычным браузерным PDF-просмотрщиком (ссылка, новая вкладка) — без
  встроенного высокого iframe/просмотрщика на странице;
- аудио и видео — дополнительные вложения.

**Что есть сейчас.**
- `TemplateDay.textContent` — текстовое содержимое дня.
- `template_attachments` kind = `file` — PDF-документы.

**Что делаем.**
- БД: отдельной колонки/режима нет; текст и PDF хранятся независимо.
- Санация HTML на сервере (`sanitize-html`/DOMPurify) при сохранении всех текстов.
- API `POST /days` **не запрещает** одновременные `textContent` и PDF-вложения.
- Frontend ментора (`days.tsx`): Quill-редактор текста + загрузка PDF-документов + аудио/видео
  в одном дне без переключателей.
- Рендер у участника/админа: сначала текст HTML, под ним «Документы (PDF)» ссылками,
  далее аудио/видео.
- Зависимости: `quill` + `sanitize-html` на сервере.
- PDF: `POST /api/uploads/file` — `application/pdf`, лимит 25 МБ (env);
  отдача `/api/uploads/file/[...path]` с `Content-Type` и `Range` (по образцу аудио-роута).

## 3. Тренировка: факт занятия ✓/✗

**Статус: подтверждено.**

В отчёте дня вместо «Активность (часы : минуты)» — поле **«Тренировка»**: отметка факта —
✓ тренировка была / ✗ не была. Минуты не собираем.

**Что есть сейчас:** `activityMinutes` (integer) + поле «часы:минуты» в `MetricBlock` (`DayReport.tsx`).

**Что делаем.**
- БД: `training_done BOOLEAN NULL` в `daily_reports`; `activity_minutes` оставить зарезервированной.
- Валидация/типы/стор: `trainingDone: boolean | null`
  (`src/lib/validate.ts`, `src/types/participantDay.ts`, `src/stores/participantDayStore.ts`).
- API: `trainingDone` в POST/PUT отчёта и GET дней.
- Frontend: переключатель ✓/✗ (третье состояние — «не отмечено»).

## 4. Пульс и давление — опциональные поля отчёта

**Статус: изменено.**

Пульс и давление — **опциональные** поля в отчёте дня: участник **может заполнить, но не обязан**.
Отдельного включения/выключения блока и настроек марафона для них **нет** — поля просто
показываются в отчёте как необязательные. Пустое значение никак не влияет на сохранение отчёта.

**Что есть сейчас:** замеры пульса в отчёте дня (`pulse_readings`, отдельная форма `PulseReadingsForm`).

**Что делаем.**
- БД: в `pulse_readings` добавить `systolic SMALLINT NULL`, `diastolic SMALLINT NULL` (давление,
  необязательно к заполнению, как и пульс).
- Frontend: в строке замера — помимо времени и пульса, поля АД (сист/диаст).
- Валидация: `systolic` (60–250), `diastolic` (40–160), систолическое > диастолическое.

## 5. Контрольные дни замеров: вес и охваты — только в эти дни

**Статус: изменено (переформулировано).**

Правила заполнения метрик по дням марафона:

| Метрика | Когда заполняется | Обязательность |
|---|---|---|
| Сон, вода, шаги (+ тренировка ✓/✗, продукты/калории) | Каждый день | Обязательно |
| **Вес и охваты** (вес, ОГ, ОТ, ОБ, ОН) | **Только в дни замеров** | Обязательно *в эти дни* |
| Пульс и давление (п.4) | Любой день | Опционально |

**Дни замеров** — параметр программы: ментор помечает день как **«день замера»** при создании
шаблона **вручную**. Для 21-дневного марафона обычно размечаются дни **1, 8, 15, 21** —
это рекомендация для ментора, а не автоматическое поведение платформы.

Участник:
- на кнопке дня в календаре — **иконка «день замера»**;
- в интерфейсе дня — **сообщение «Сегодня день замера»**;
- блок **«Вес и охваты»** есть **только** в день замера, в остальные дни его **нет**.

**Что есть сейчас:** поля `weightKg, chestCm, waistCm, hipCm, legCm` (`daily_reports`) доступны
каждый день.

**Что делаем.**
- БД: `template_days.is_measurement_day BOOLEAN NOT NULL DEFAULT false`.
- API дней: возвращать `isMeasurementDay`; в неконтрольные дни поля замеров **игнорируются сервером**.
- Frontend: ментор — переключатель «День замера» у каждого дня (только ручная разметка,
  без авто-кнопки); участник — иконка в `DayNavbar`, пометка в
  `DayHeader`, блок «Вес и охваты» только при `isMeasurementDay`.
- Рейтинг: `entryWeight`/`currentWeight` — первый/последний замер веса.

## 6. Доступ к дням после завершения марафона

**Статус: подтверждено.**

- После завершения потока доступ к материалам всех дней **сохраняется** на чтение.
- Страница результатов **доступна**.
- **Редактировать** отчёты после финиша **нельзя**.

**Что есть сейчас.**
- Календарь при `finished` редиректит на результаты
  (`src/pages/dashboard/marathon/[streamId]/index.tsx`) — материалы через UI недоступны.
- API при `finished` считает все дни редактируемыми (`isEditable = true`) — отчёты можно править.

**Что делаем.**
- Backend: `isFinished` в ответах дней; `isEditable = isDayAccessible(...) && !isFinished`;
  POST отчёта / PUT `/api/reports/[reportId]` — 403 для `finished`.
- Frontend: в карточке завершённого марафона — кнопки «Результаты» и «Материалы»; на странице
  завершённого марафона — переключатель «Результаты | Материалы»; материалы читаются без правки.

## 7. Предстартовая страница марафона *(изменено)*

**Статус: изменено (перенесено в создание шаблона).**

Страница потока, доступная **всем пользователям до старта** марафона — приветственная. Ментор
прикрепляет к ней **текст (Quill) и материалы (аудио, видео, PDF)** — что за марафон, как
готовиться, план.

**Решение:** материалы задаются **один раз на шаблоне** и действуют для всех потоков.
Переопределение под конкретный поток не делаем.

Предстартовая страница настраивается **в создании шаблона отдельным шагом**:
1. Шаг 1 — основная информация;
2. Шаг 2 — **предстартовая страница** (текст в редакторе + вложения);
3. Шаг 3 — дни марафона.

Шаг 2 можно пропустить; заполнить/изменить его позже можно со страницы шаблона
(кнопка «Предстартовая страница» → `/mentor/templates/[id]/intro`).

**Что есть сейчас.**
- Публичная страница `src/pages/streams/[id]/index.tsx` (`GET /api/streams/[id]`) показывает:
  описание шаблона, длительность, дату старта, статус, ментора, число участников и кнопку записи.
- Черновик реализации: секция в редактировании шаблона и рендер на публичной странице.

**Что делаем.**
- БД: на `marathon_templates` — `introText TEXT NULL` — приветственный текст (HTML от Quill);
  вложения — строки в `template_attachments` со `scope = 'intro'` (`templateDayId = NULL`), п.1.
- API:
  - `GET /api/streams/[id]` (публичный) — возвращает `intro: { text, attachments[] }`;
  - ментор: `GET/PUT /api/marathons/[id]` принимает `introText` + POST вложений `scope=intro`.
- Frontend:
  - создание шаблона: новая страница-шаг `/mentor/templates/[id]/intro`;
  - ментор-редактирование шаблона: кнопки-переходы «Предстартовая страница» и «Дни»;
  - публичная страница потока — блок «Материалы для подготовки»: текст, аудио/видео-плееры,
    ссылки PDF;
  - записанные участники видят блок до старта (и после старта/финиша как «приветствие»).

## 8. Комплект «PDF + аудио» в дне марафона

**Статус: новое (реализуется 07.09.2026).**

PDF и аудио в днях марафона — это **пара/комплект**: один PDF + один аудиофайл = один материал.
Ментор создаёт комплект одним действием. Участник видит карточку с аудиоплеером и кнопкой
«Открыть PDF в новой вкладке» — без встроенного предпросмотра PDF. Одиночные PDF/аудио/видео
остаются поддерживаемыми.

**Что делаем.**
- БД: `template_attachments.pair_id UUID NULL`. У двух строк пары (`kind='file'` + `kind='audio'`)
  внутри одного дня одинаковый `pair_id`; у одиночных вложений — `NULL`.
- Uploads API: `POST /api/uploads/pair` — multipart `templateId`, файлы `pdf` и `audio`;
  возвращает `{ pairId, pdf, audio }`.
  > Обновлено позже: отдельный эндпоинт и компонент `PairManager` убраны. Комплект теперь
  > собирается на клиенте в редакторе вложений (`src/components/mentor/AttachmentsEditor.tsx`):
  > медиа и PDF грузятся обычными эндпоинтами, а `pairId` генерируется клиентом. Логика —
  > чистые функции в `src/lib/attachmentEditor.ts`.
- API дней: `pairId` принимается/сохраняется/возвращается в `attachments[]`.
- Frontend ментора: блок «Комплекты PDF + аудио» — добавление пары двумя файлами сразу,
  удаление всего комплекта.
- Frontend участника/админа: комплекты рендерятся карточками с аудиоплеером и кнопкой
  «Открыть PDF в новой вкладке»; одиночные вложения — как раньше.

## Порядок выполнения

С миграцией и проверкой `npm run build` после каждого шага:

1. **П.5 Контрольные дни замеров** — флаг дня + блок «Вес и охваты» (высокий).
2. **П.3 Тренировка ✓/✗** — замена поля (высокий).
3. **П.6 Доступ после финиша** — запрет правок + доступ к материалам (высокий).
4. **П.1 Мульти-аудио и мульти-видео** — таблица вложений (средний; база для п.2 и п.7).
5. **П.2 Quill + PDF** — поверх схемы вложений (средний).
6. **П.7 Предстартовая страница** — текст + вложения на публичной странице (средний).
7. **П.4 Пульс и давление** — опциональные поля (низкий).

### Разбивка по сессиям

**Сессия 1 — отчёты участника и доступ после финиша:**
1. **П.5 Контрольные дни замеров** — флаг дня, ручная разметка, блок «Вес и охваты» только в дни замеров.
2. **П.3 Тренировка ✓/✗** — замена «Активность (часы:минуты)» на факт тренировки.
3. **П.6 Доступ к дням после завершения** — запрет правок после финиша + «Результаты | Материалы».
4. **П.4 Пульс и давление** — опциональные поля АД в форме замеров.

> Критерий завершения сессии: `npm run build` без ошибок, отчёт дня и календарь проверены вручную.

**Сессия 2 — материалы дней и предстартовая страница:**
1. **П.1 Мульти-аудио и мульти-видео** — таблица `template_attachments`, uploads API, списки плееров у ментора/участника/админа.
2. **П.2 Quill + PDF** — всегда Quill для текста; текст и PDF в одном дне; санация HTML; PDF-вложения под текстом; рендер у участника.
3. **П.7 Предстартовая страница** — шаг создания `/intro` + текст и вложения шаблона на публичной странице потока.

> Критерий завершения сессии: `npm run build` без ошибок; ментор может наполнить шаблон
> материалами и запустить поток; участник видит материалы дня и предстартовый блок.

Внутри каждой сессии выполнять пункты по порядку и запускать `npm run build` после каждого пункта.

## Решено

- **П.2** — только Quill для текста; настройки `text_editor: plain | quill` нет.
  У дня могут быть **и текст, и несколько PDF одновременно**. PDF показывается под текстом
  списком «Документы (PDF)» и открывается обычным браузерным просмотром.
- **П.4** — пульс и давление просто опциональные поля, без включения/выключения через настройки.
- **П.5** — «дни замеров» ментор размечает **только вручную**; автоматическая кнопка
  «разметить 1/8/15/21» не нужна.
- **П.7** — предстартовые материалы один раз на **шаблоне**, редактируются на отдельном шаге
  создания `/mentor/templates/[id]/intro`, действуют для всех потоков.
- **П.1 (ограничение)** — стабильность `id` дней и безопасное повторное редактирование шаблона
  с уже прикреплёнными вложениями **сейчас не делаем**. Текущее поведение `POST /days`
  (удалить и пересоздать дни) сохраняется; upload не пишет строки вложений, а возвращает
  метаданные, строки `template_attachments` создаются при сохранении дней/шаблона.
